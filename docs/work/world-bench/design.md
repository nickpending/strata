# Design: world-bench

## Purpose

The backbone every later layer of strata reads: one record of what happened, applied to small parts that own one fact each, driven by a clock and watched event by event from a local page, so that relationships, perception, minds and conversation can be built on top of something whose every change is visible and whose seams hold.

## Form

One Bun process holds the engine and serves the bench; the engine is a library the server and the tests call the same way. The repository is new, so nothing is extended; the licence for each piece is the exploration line named.

1. Layout. `package.json` (Bun 1.4, TypeScript strict, zod 4 as the one dependency; `bun test`, `tsc --noEmit`, biome as the checks, the ember toolchain), `world/` (authored definitions), `src/engine/` (definitions, things, events, rules, clock, store, snapshot), `src/server/` (routes and the CLI), `bench/` (the page), `tests/`.

2. Definitions (`world/`, TOML, read with Bun's native TOML import, validated by zod schemas in `src/engine/definitions.ts`; a definition that fails validation refuses boot naming the file, the path and the rule). Files: `world/world.toml` (`[rules] offer_window_ticks`), `world/rooms/chrome-cassette.toml` and `world/rooms/back-room.toml` (`id`, `name`, `description`, `exits = { east = { to = "back-room", travel_ticks = 1 } }` and the matching `west`), `world/people/rogue.toml`, `glitch.toml`, `mux.toml` (`id`, `name`, `location` = the room id, `ties = [{ target, kind, note }]` re-authored from reverie's NPC-to-NPC ties only: rogue->glitch wary tolerance, glitch->rogue lying low on her tolerance, mux->glitch a regular for parts), `world/items/*.toml` (`id`, `name`, `description`, `holder` = the person id; the three re-authored from reverie: stimpak held by glitch, charge-cell by mux, data-shard by rogue). Holder is one scalar on the item, so an item held by none or two cannot be written, and no person lists what it holds. Travel times and the offer window are authored world data, edited in these files, never defaulted in code. No prose beyond `description` and tie notes exists yet; voice prose is a later block's layer.

3. Things and parts (`src/engine/things.ts`). A thing is an id plus its parts; a part is a pure reducer `{ initial(definition) -> state, apply(state, event) -> state }` that returns its state unchanged for every event that does not concern it, and never reads another part. Each fact has one owner: a person's `location` part (`{ room }` or `{ transit: { from, to, arrivesAt } }`), a person's `ties` part (the authored list, inert in this block), an item's `holder` part (a person id), an item's `offer` part (`none` or `{ to, offerEvent, until }`; the giver is the item's holder, never a second copy), and the clock's `tick` and `schedule` parts. Rooms carry no live part in this block: who is present and who holds what are views computed from the owning parts in the snapshot, never a second copy.

4. Events (`src/engine/events.ts`). One envelope `{ id, tick, seq, kind, subkind, actor, targets, place, visibility, cause, payload }`, `id` = `e<seq>`. A registry maps each subkind to its zod payload schema and its visibility `{ audience: "place" | "none", narrow?: { <field>: "participants" } }`. The first block's registry: `physical.depart { from, exit, to, travelTicks, arrivesAt }` (place from), `physical.arrive { from, to }` (place to, cause the depart id), `speech.say { words }`, `speech.say-to { words }` (targets the addressee), `speech.whisper { words }` (narrow words -> participants, so the room learns a whisper passed and only actor and target get the words), `exchange.offer { item, until }`, `exchange.accept { item, from }`, `exchange.refuse { item, from }`, `exchange.lapse { item, from, to }` (the fourth give subkind, added under the line-135 licence so an unanswered offer's end is in the log), `time.tick {}` (audience none). Kind names what happened and `cause` names why, so an operator-made depart is `physical.depart` with `cause: operator`; no `authored` family is emitted in this block, and the family stays reserved for operator-made events that are no thing's action. Adding a subkind is one registry entry and one rule; no part or reader changes.

5. Rules (`src/engine/rules.ts`). An action is `{ actor, verb, ...fields }`, one zod schema per verb, validated first by its schema and then by one pure rule over the snapshot that returns either `{ refused: { code, message } }` or the events to record. `code` is from a closed set: `no-such-exit`, `in-transit`, `not-in-room`, `self-target`, `not-holding`, `already-offered`, `not-offered-to-you`, `giver-absent`; tests and the page read the code, the message is for the operator. `depart(exit)` needs the actor in a room with that exit; `say(words)` needs the actor in a room; `say-to(target, words)` and `whisper(target, words)` need a target other than the actor and both in the same room; `offer(target, item)` needs the actor to hold the item, the item unoffered and the target in the actor's room, and sets `until = tick + offer_window_ticks`; `accept(item)` and `refuse(item)` need the item offered to the actor, and accept also needs the giver, read from the item's holder part, in the actor's room. A refusal is returned to the caller alone; nothing is written. Cause on every operator-made event is `operator`.

6. The clock (`src/engine/clock.ts`). Its `schedule` part listens: a depart schedules `physical.arrive` at `arrivesAt`; an offer schedules `exchange.lapse` at `until`; an accept or refuse of that item drops the pending lapse, the one mechanism that ends it. `step()` appends `time.tick` for tick+1, then fires every entry due at that tick in insertion order, each as an event whose cause is the scheduling event's id. Game time shown in the bench is `tick * tickMinutes`, with `tickMinutes` taken from `--tick-minutes`, required on every launch and in `boot()`, and refused with a message naming the flag when absent.

7. Applying an event (`src/engine/engine.ts`, `src/engine/store.ts`). `act(action)` and `step()` share one path: validate the event's payload against its schema, append it to `events`, run every part's reducer over its own row in `state(thing, part, json)` and write the row back, compute the witnesses (every person whose location is the event's place after application, plus actor and targets), write each witness a redacted copy to `witnessed(event, witness, json)` (narrowed fields dropped unless the witness is a participant), all in one `bun:sqlite` transaction. Live state has one home, the `state` rows; the engine holds nothing between calls. `boot(defs, { tickMinutes, dbPath })` creates the file afresh from the definitions, so a second boot from the same files is byte-identical in `state`, and a reset is a reboot. `snapshot()` reads the rows and returns every thing's current parts plus the derived views (room presence, holdings, in-transit list, pending offers, due schedule).

8. Server and bench (`src/server/`, `bench/`). `bun run src/server/main.ts --tick-minutes <n> [--world world] [--db ./strata.sqlite] [--port 4800]` (the three bracketed defaults as shown, the database file gitignored, `--tick-minutes` required) binds `127.0.0.1` explicitly and serves `GET /` (`bench/index.html`), `GET /bench/*` (the `bench/` directory as static files, which is how `app.js` and the panels reach the browser), `GET /api/snapshot`, `GET /api/events?since=<seq>`, `GET /api/received/<thing>`, `GET /api/verbs` (each action schema as JSON Schema through zod's `toJSONSchema`), `POST /api/actions` (the action; 200 with the events, 422 with the refusal), `POST /api/step`, `POST /api/reset`. The page is plain HTML and vanilla script: `bench/app.js` mounts every panel in `bench/panels/`, and this block adds `panels/world.js`, which renders the two rooms with who is present, what they hold and their ties, the in-transit list, the items with any pending offer, the clock (tick, game time) and the schedule, an act form built from `/api/verbs` (actor, verb, the verb's fields) that shows a refusal's code and message inline, a step button, a reset button, and the history with each event's envelope and payload, plus a per-person view of what that person received. The page refetches the snapshot and the new events after every action or step; no push channel in this block.

9. Proof. Unit tests per rule (each refusal by code and each emitted event), per part (the reducer ignores events that do not concern it), the clock (order within a tick, nothing early, a lapse dropped by accept or refuse), redaction (whisper words reach actor and target only), boot (determinism across two boots; refusal of a missing tick length; refusal of a definition that fails its schema), and an HTTP test that boots the committed world files, departs, steps to the arrive, offers, accepts and reads the snapshot and the history through the routes. The page is checked by fetching `/`, `/bench/app.js` and `/bench/panels/world.js` through the server and getting each with its content type (no browser automation).

Acts on the gap: It builds the engine the gap names: typed definitions boot into live state owned by parts; rules validate each authored action into recorded events of the first-block kinds or refuse it to the author with a typed code; each event is applied only by the parts it concerns; the clock fires scheduled arrivals and offer lapses; and the bench shows every thing's state, the history and each witness's copy after every step.

## Commitments

- One language and one process: the engine is a TypeScript library on Bun that the server and the tests call identically, and the bench page is served by the same process that holds the world, bound to the loopback address.
- Each fact has exactly one owning part and one home, a row in the state table; every other view of it is computed from the snapshot and never stored twice.
- Parts are pure reducers over events and never read another part; rules are pure functions over the snapshot and never write state; the engine alone appends, applies, witnesses and persists, in one transaction.
- Every event in the log passed its subkind's schema, and every witness holds a redacted copy made by code from the subkind's visibility, so what a thing may know is enforced before any mind exists.
- Definitions are TOML validated by zod at boot and never written at runtime; the operator changes the world only through actions, and the tick length is a required launch flag with no default.
- Adding an event subkind is one registry entry and one rule; no part, reader or page changes, and the page's act form is built from the action schemas the engine serves.

## Sacrifices

- No resume: a restart boots afresh from the definitions and the previous run's database is replaced, so a run is not continued across launches. (not a case: the bench has no runs to continue: the repository holds no code yet and every run is a fresh boot by design)
- No push channel: the page refetches after each action or step, so a second viewer of the same world would see changes only on its own next action. (not a case: one operator views the bench on one machine bound to loopback; no second viewer exists to miss an update)
- Rooms carry no live part in this block, so a later block that gives rooms state (a brownout, a door) adds the first room part rather than extending one. (not a case: no first-block event changes a room, so there is no room state to hold)
- No voice prose in the definitions yet; the prose layer arrives with the block that speaks. (not a case: nothing speaks in this block: no model runs and no event carries per-NPC wording)

## Risk

If the seam leaks, a rule writing state, a part reading another, a view stored instead of computed, the engine becomes reverie again: state written in several places by several paths, and the next layer cannot trust the log. The tests pin purity per part and per rule, but a builder can still route around them; the review reads for it. Lesser: a wrong witness rule (presence computed before application rather than after) would give the departing mover the room's next events or deny the arriver its own arrival, visible immediately in the bench's per-person received view.

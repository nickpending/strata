# Design: bench-driver

## Purpose

Two users of the bench that need no hand on the form: a driver that proves, after every action and step, that the live state is exactly what the log says and the world's invariants hold, and a player that works the bench page in a real browser toward an instruction, reading the page as text and asking Jev one yes/no per candidate control, with a language model only for the target and the words, every loop shown, whose histories are the corpus the mind blocks read. Multi-step actions are served by one mechanism: the engine exposes every pending state with its resolver, verbs and expiry, and the player's goal is a typed end state checked by code, so code resolves what stands between now and the goal before the clock kills it.

## Form

A driver that calls the engine library and a player that works the bench page in a real browser, each a CLI and a module, plus a committed corpus.

1. Layout. `src/driver/` (random actions, replay oracle, invariants, run loop, `main.ts`), `src/player/` (Jev client, language-model client, page reading, candidates, the pre-registered rule, the loop, scoring, `main.ts`), `corpus/runs/<run-id>/` and `corpus/goals/` (committed data), `tests/` for each. `package.json` gains `@voidwire/apiconf` 0.2.0 (the key, published 2026-03-31) and `playwright` 1.64.1 (published 2026-10-14, chromium build 1248 cached on this machine; `bunx playwright install chromium` is the one setup step, and a test that cannot launch the browser fails naming it) and scripts `driver`, `player`, `score`. The seeded generator is a small in-house function.

2. Random actions (`src/driver/actions.ts`). `randomAction(snapshot, verbs, rng)` returns an action object, legal or illegal by draw: the actor is one of the people (or, one draw in sixteen, a name that is no person, including inherited-key names like `constructor`); the verb is drawn from `verbs()`; each field is filled from the id space the snapshot gives (every room's exits, every item, every person, a short words string), with a bias towards the actor's own room, holdings and pending offers so legal actions are common, and with inherited-key names, empty strings and absent fields drawn now and then so the schemas and the closed refusal codes are hit. `rng` is a seeded 32-bit generator in `src/driver/rng.ts`; the same seed yields the same sequence.

3. Replay (`src/driver/replay.ts`). `project(defs, events)` composes `initialRows(defs)` with `applyPart` over every row for each event in seq order and returns the rows it reaches; it persists nothing and touches no store. `compare(live, replayed)` sorts both by (thing, part) and returns the first difference `{ thing, part, event, live, replayed }` or null, `event` being the last event applied. The oracle reads the live rows through `engine` (a `rows()` accessor added beside `snapshot()`, returning `store.readState()`) and the log through `engine.events()`.

4. Invariants (`src/driver/invariants.ts`). `check(engine)` returns every violation, each typed `{ invariant, thing, detail }`, over the snapshot, the log and the received copies: `holder` (every item's holder names a person), `location` (every person is in a room the definitions hold, or in transit to one with a `physical.arrive` for that person due at its `arrivesAt` in the schedule), `redaction` (for every event whose registry entry narrows a field, every copy held by a thing that is neither actor nor target lacks that field; the entries are read from `registry`, never listed), `log` (every event's payload parses against its subkind's schema). The fifth, `refusal`, is the run loop's: it snapshots the event count and the rows before an action and asserts both unchanged after a refusal or an invalid action.

5. The driver loop (`src/driver/run.ts`, `src/driver/main.ts`). `runDriver({ worldDir, tickMinutes, seed, actions, stepEvery })` boots into a temporary database (under the OS temp dir, removed at the end), then for `actions` iterations draws an action, calls `act`, and every `stepEvery` actions calls `step`; after every call it runs replay and `check` and stops at the first failure, returning `{ ok: false, at: <iteration>, failure }`. Each iteration's outcome is tallied: recorded by verb, refused by code, invalid. The report `{ ok, seed, actions, steps, tally, checks }` is printed as JSON by `bun run src/driver/main.ts --seed <n> --actions <n> --tick-minutes <n> [--world world] [--step-every 5]`, exit 1 on a failure naming it. No model anywhere.

6. The Jev client (`src/player/jev.ts`). `decide(state, questions, options)` posts `{ model: "typesafe/jev-1.13", state, questions }` to `https://openrouter.ai/api/alpha/decisions` with the apiconf key `sable-openrouter` (`getKey` from `@voidwire/apiconf`), returns `{ ok: true, answers, costUsd }` with each answer typed noul `{ noul }` or choice `{ choice, confidence, probabilities }`, or `{ ok: false, refusal: { kind: config | network | status | parse, message, status? } }`; `options.endpoint` and `options.key` let a test stand a local server in. The same shape as ember's client, written here, never imported.

7. The language-model client (`src/player/words.ts`). `complete(prompt, schema, options)` posts an OpenAI-shaped chat completion to `https://openrouter.ai/api/v1/chat/completions` with the same key, model `anthropic/claude-haiku-5.5`, asking for one JSON object matching `schema` (a zod schema, validated on return), and returns `{ ok: true, value, costUsd }` or the same typed refusal as the Jev client. It is called twice per run at most: `target(instruction, page)` and `words(target, page)`. `options.endpoint` and `options.key` stand a test server in.

8. Reading the page (`src/player/page.ts`). `readPage(page)` returns `{ text, controls }`: `text` is Playwright's `ariaSnapshot()` of the body (headings, text, every control with its label, options and selection), and `controls` is every `button`, `select`, `input` and `textarea` as `{ id, kind, label, value, options, enabled }`, the label from the wrapping `<label>` or the button's own text. A control with an empty label is a refusal of the page, never a candidate. The candidates (`src/player/candidates.ts`) are `(control, option)` pairs for each select option not currently selected, a press for each enabled button, and a typed value for each input, each with a one-sentence description built by code ("set verb to whisper", "press Act", "type the words into words").

9. The target (`src/player/target.ts`, `src/player/goal.ts`). The run's target is a typed end state, never an action. `src/player/goal.ts` owns the end-state vocabulary the player and score share: `expectSchema` (`{ holder: { item, person } }`, `{ location: { person, room } }`, `{ said: { person, subkind } }`, `{ outcome: "no-such-action" }`, moved here from score.ts unchanged) and `holds(expect, base)` (moved from score.ts:91 unchanged, reading `/api/snapshot` and `/api/events` through the bench's routes). `target(instruction, page)` gives the model the instruction and the people, items, rooms and speech kinds the page shows, and asks for `{ kind: "goal", expect, needsWords }` or `{ kind: "no-such-action", reason }`. Code checks every id the end state names against the page: a person, item, room or subkind the page does not show is `no-such-action` with the mismatch named, whatever the model said. The schema keeps the recorded `action` kind as a type only, so run files written before this change still parse; the player never produces it. When `needsWords`, `words(goal, page)` asks the model for the line (the only free text in the run); Jev never writes it.

10. The rule (`src/player/rule.ts`). Pre-registered in code with `RULE_AUTHOR`; `T_DONE` and `T_ACT` keep their calibrated values. Each loop asks Jev, over a state rendered by code (the instruction, the end state in words built by code from `expect`, the words if any, then the page text, which now carries the pending states), one noul `done` and one noul per candidate, all in one `decide` call; the answers are recorded every loop. Then code decides, in this order: (a) `reached` when `holds(goal.expect)` is true on the bench now, the done noul recorded and deciding nothing, the outcome keeping it as `done`; (b) `resolve` when a pending state stands between now and the goal: the first entry of the snapshot's `pending` with a resolution whose `after` satisfies the end state (the same predicate `holds` applies to a snapshot, `satisfies(expect, after)`, one function for both) gives the next action, that resolution's next form move, recorded with the pending state it serves; when no resolution does but the entry's `due.after` satisfies it (an arrival), the next action is `press Step`; (c) otherwise `choose()` performs the highest candidate at or above `T_ACT`, or stops `stuck`, with `press Step` removed from the candidates while any pending state has a resolution whose `after` satisfies the end state. The next form move of a resolution's action is derived from the controls as read: the first control among actor, verb and each of the action's fields whose value differs from the action's gives the candidate `set <label> to <value>`; when all agree, `press Act`. When the derived move is not among the page's candidates, the loop stops `stuck` naming the pending state, never guessing. Nothing in (b) names an action kind: an offer, an arrival and any later pending state are served by the same lookup.

11. The loop (`src/player/run.ts`, `src/player/main.ts`). `runPlayer({ instruction, url?, worldDir, tickMinutes, headed, maxLoops, runDir })` hosts the bench itself through `startServer` on an ephemeral port with a fresh world when `url` is absent, launches chromium (visible when `headed`), opens the page, asks for the target (ending at once with `no-such-action` when that is the answer), then loops: read the page, read the snapshot (its pending states) and whether the end state holds through the bench's routes, render the state, ask the rule, print the loop (the state text sent, every question with its answer, the action performed or the stop) to stdout as it happens and append it to `loops.jsonl`, perform the action in the browser (select an option, press a button, type a value) and wait for the page to settle. It ends on `reached`, `stuck`, `no-such-action`, the loop ceiling, or a refusal from either client, which it names. At the end it writes `run.json` (instruction, target (the typed goal), parameters, outcome, loops, each model call with its cost, total cost), `events.jsonl` and `received.jsonl` read through `/api/events` and `/api/received/<person>` for every person, under `corpus/runs/<run-id>/`, `<run-id>` the UTC start time. `bun run src/player/main.ts "<instruction>" --tick-minutes <n> [--url <bench>] [--headed] [--max-loops 24] [--world world] [--corpus corpus/runs]`.

12. Goals and scoring (`src/player/score.ts`, `corpus/goals/`). A goal file is `{ set, author, goals: [{ id, instruction, expect }] }` where `expect` is the end state of `src/player/goal.ts`, checked by code (`holds`) against the run's final `/api/snapshot` and `/api/events`: `{ holder: { item, person } }`, `{ location: { person, room } }`, `{ said: { person, subkind } }`, `{ outcome: "no-such-action" }`. `score(goalsFile)` runs the player on each goal with its own fresh bench and records `<set>.score.json` `{ reached: { held, of }, perGoal: [{ id, outcome, loops, costUsd }] }`; with `--sweep` it replays the recorded loops over a grid of `T_ACT` values with reached taken from each loop's recorded `held` and `resolve` loops followed as recorded, `T_DONE` held at its calibrated value in every row of the `{ done, act, held }` results, and prints the best; the calibrated constants are not re-swept. `score` refuses a goal file whose `author` equals `RULE_AUTHOR`. The calibration set `corpus/goals/calibration.json` (the builder's) sets the thresholds; the blind set `corpus/goals/blind-2.json` is written after the merge, by a fresh agent that has read neither `rule.ts` nor `blind-1.json` (blind-1 is spent: its misses shaped this change) by an agent that is not the rule's author, which is why its score is a post-merge walk: a blind set that exists while the rule is written is not blind.

13. The labelled-control rule (`tests/page.test.ts`). With the bench hosted and chromium launched, every `button`, `select`, `input` and `textarea` on the page has a non-empty label, and the test names any that does not; this is the gate behind the rule that every strata page's controls carry a clear label.

14. Proof. Driver: a seeded run of 400 actions on the committed world passes every check and tallies at least one event of every subkind and at least one refusal of every code; each of four mutations (the engine writes only the actor's rows, the location reducer ignores arrive, act records on refusal, the whisper narrow dropped) turns a named check red. Replay: `project` over a hand-built log equals rows computed by hand. Player, against local stand-ins for the decisions endpoint and the chat completions endpoint returning scripted answers, with the real browser on a hosted bench: the loop reads the controls with their labels, offers only candidates the page has, performs selects, presses and typing, stops on `reached` when the end state holds whatever the done noul says, on `stuck` when nothing passes, at the loop ceiling, and names each refusal kind; a target naming a verb the page lacks ends in `no-such-action` without a loop; the run files are written with the history read from the bench and costs summed; the labelled-control test passes on the page and fails on a page with one unlabeled button. The real endpoints are called only by the calibration run the builder performs, whose cost is recorded in its score file. Pending states: `pending` on a booted world after an offer and after a depart equals values derived by hand (opened, due with its after, the resolutions with theirs), through the engine and through `/api/snapshot`, and stepping to an offer's `due.at` records its lapse and empties `pending`; the page shows each with its resolver, verbs and expiry; with scripted nouls that score `press Step` above every other candidate on every loop, each give goal (a holder end state reached by offer then accept) reaches its end state with no `exchange.lapse` in the run's history and no Step pressed while the offer stood, and a run with the derivation removed lapses (the mutation).

15. Pending states (`src/engine/pending.ts`, `src/engine/engine.ts`, `src/server/routes.ts`, `bench/panels/world.js`). Multi-step actions share one shape: an action opens a pending state that the clock will close at a tick unless someone resolves it first. The clock's schedule is already the one home of every such deadline (clock.ts:29-58: a depart's arrive, an offer's lapse), so a pending state is a schedule entry, and nothing about it is stated a second time: `pendingOf(rows, defs, snapshot)` derives each one by running the engine's own rules and reducers. For each schedule entry it returns `{ opened: <the cause event: id, subkind, actor, targets, payload>, due: { at, fires: <the entry's subkind>, after }, resolutions: [{ by, action, after }] }`, where `resolutions` are the actions, among every verb from `verbs()` by every person over the world's ids (exits, items, people, a placeholder line for words), that `rule()` records now and after whose events, applied to a copy of the rows through `applyPart` (the composition replay.ts:18 uses), that entry is gone from the schedule; and each `after` is `{ holders, locations }`, the item holders and person locations of the rows reached. The draft-to-event step `record()` performs is exported once and used by both, never copied. `engine.pending()` is its own accessor, never part of `snapshot()`, which the engine calls on its own apply path four times per act or step (engine.ts:101, 110, 112, 149), so the engine's recording and the driver's oracles never pay for the sweep; the `/api/snapshot` route composes it into its body as `pending` beside the snapshot's fields, and every route body that hands the page a snapshot does the same; `buildSnapshot()` and `snapshot()` are unchanged. On the committed world an offer gives two resolutions, the target's accept (after: the target holds the item) and refuse (after: the giver does), and its due firing is the lapse (after: the giver does); a transit gives no resolution and its due firing is the arrival (after: the walker in the destination room). Nothing in `pending.ts` names a verb, a subkind or a part: a later trade or unlock that schedules its deadline is a pending state with its resolutions the day its rule exists. The page renders a `Pending` section from `pending`, one line per state built by code from its fields ("exchange.offer e1 by rogue to glitch, data-shard: resolved by glitch accept, glitch refuse; at tick 2 the clock fires exchange.lapse"; "physical.depart e3 by glitch: no one resolves it; at tick 1 the clock fires physical.arrive"), so Jev's state and a person watching read the same thing; it adds no control.

Acts on the gap: It supplies the users the gap names: a random driver whose oracle is replay-equals-state plus the invariants, run after every action and step on a seeded sequence; a browser player that reads the bench page as text, asks Jev one yes/no per candidate control and one for the goal, performs the winner and loops, with a model only for the target and the words, recording every loop and every history; and the scoring that measures the player on goal sets by expected end states. Multi-step actions are met by one mechanism: the engine derives each pending state from the clock's schedule, with its resolutions and their results found by running its own rules and reducers; the player's goal is a typed end state checked by code; and code derives the resolving move for a pending state that stands between now and the goal, before the clock's expiry.

## Commitments

- The driver calls the engine library (boot, act, step, events, received) and nothing lower; the player calls the page as a person does, through a real browser, and reads the history back through the bench's own routes; the definitions are never written.
- The replay oracle composes the engine's own initialRows and applyPart over the log and compares state rows; it keeps no second copy of any fact and persists nothing.
- The invariants read the registry, the schemas and the typed views; no subkind, field or code is listed a second time in the driver.
- The player's candidates are read from the page each loop, one noul per candidate plus one goal-reached noul, recorded, in one Jev call; Jev never writes text, and a language model writes only the typed target and the words, each checked by code against what the page offers.
- An instruction with no matching action ends in no-such-action; nothing invents a verb, an actor, an item or an exit the page does not show.
- Every loop's request and answer are printed as they happen and recorded, and the browser can be watched.
- The rule's thresholds are constants committed with the calibration goal set and its score before any blind set exists; a blind goal set carries an author other than the rule's recorded author, which score enforces by refusal, and is scored by expected end states after the merge.
- Every player run is recorded as typed files under corpus/runs/<run-id>/ as it happens, with every question, answer, model call and cost, so a later block reads the corpus without the engine that produced it.
- A refusal from either client stops the player naming its kind; the driver needs no model at all.
- Every control on a strata page carries a clear label, held by a test that fails naming any that does not.
- A pending state is a clock schedule entry, and its resolutions and their results are derived by running the engine's own rules and reducers on a copy of the rows, served by its own engine accessor through the bench's routes, never on the engine's apply path, and shown on the page; nothing about a pending state is stated a second time and no verb, subkind or part is named in deriving it.
- The player's goal is a typed end state from the closed set (holder, location, said, no-such-action), checked by code against the bench; reached is that check, never a model's claim, and the done noul is recorded but decides nothing.
- While a pending state whose resolution leaves the goal's end state stands, the next action is derived by code from that resolution and the clock is never stepped past its expiry; no action kind is named in that derivation.
- T_DONE and T_ACT keep their calibrated values; nothing is re-tuned against a blind set, and the blind walk uses a fresh set written by an agent that has read neither the rule nor an earlier blind set.

## Sacrifices

- The blind goal set and its score come after the merge, as a walk: a blind set that exists while the rule is written is not blind, so the worktree proves scoring on the calibration set and the blind score runs once the rule is on main. (not a case: no blind set can exist before the rule is on main: the rule's author is the builder, and the set is written against the merged rule by another agent)
- The player's text is one model-written line per run, when the target needs words; there is no voice and no persona, so the corpus carries plain lines until the block that speaks. (not a case: nothing speaks in a voice in this block: voice prose is the speaking block's layer, as world-bench's design records)
- The driver's actions are drawn from a biased uniform grammar with no coverage feedback; it finds what random reaches, not what a search would. (not a case: the block's paths are a closed set, ten subkinds and eight refusal codes, and the driver criterion requires each to appear in one seeded run's tally)
- Jev and the model are not deterministic, so a player run is not reproducible from its parameters; the corpus is committed because the run cannot be re-made. (0 of 32 32 moments, 3 reps each, 96 answers)
- The replay oracle cannot catch a wrong reducer, since live and replay share it; the invariants carry that case, and the mutations prove which oracle catches which break. (not a case: a wrong reducer is the invariants' case by design, and the location-reducer mutation in the criteria proves an invariant catches it)
- The player sees only what the page shows; a fact the bench does not render is one the player cannot reach, so a later block's panel must show what its goals need. (not a case: every first-block fact (rooms, presence, holdings, ties, transit, offers, clock, schedule, history, received copies) is on the page, read in verify.txt's snapshot)
- The calibrated T_ACT was set under the rule before this change (no pending precedence, reached by the done noul) and is kept, not re-swept, by the operator's condition; the calibration score records the old rule's runs. (9 of 9 corpus/goals/calibration.score.json)
- Every snapshot the bench serves tries each verb by each person over the world's ids through the rules to find the pending states' resolutions; the cost grows with people, verbs and ids, bounded on the committed world and paid only while a schedule entry stands. (not a case: a cost on every snapshot route read while a schedule entry stands, not a usage case: the committed world has three people, three items and two exits, so the tries are bounded by people times verbs times ids, and the engine's own apply path never pays it)
- A pending state is seen only when it has a schedule entry; a later wait with no deadline would need one before the player could see it. (0 of 2 src/engine/clock.ts schedulePart)

## Risk

If the player's rule is tuned to goals its author wrote, the calibration score means nothing and the blind set is the only test; a builder that reads a blind set before registering the rule defeats the method, which is why none exists before the merge. If the model's target is trusted without the code check against the page, the player can chase an action the bench lacks and loop to the ceiling; the check is what makes no-such-action certain. Lesser: a driver whose action grammar never reaches a refusal code or a subkind leaves that path untested, visible in the tally the criterion reads. If the derived move is missing from the page, the loop stops stuck naming the pending state rather than letting Jev press Step.

# Design: pending-states

## Purpose

Multi-step actions are served by one mechanism: the model's target is a typed plan, the end state and the ordered actions that reach it, code performs each step, and the engine exposes every pending state with its resolver, verbs and expiry, so code resolves or waits out what stands between one step and the next before the clock kills it, and reached is the code check of the end state, never a model's claim.

## Form

Pending states served by the engine and shown on the page, and a player whose goal is a typed end state, over the bench-driver player already on main.

1. Layout. New `src/engine/pending.ts` and `src/player/goal.ts`; changed `src/engine/engine.ts` (the draft-to-event step exported, `pending()` added), `src/engine/rules.ts` (`fieldIds()` added beside `verbs()`), `src/driver/actions.ts` (`fill()` draws its whole-world choice from `fieldIds()`), `src/server/routes.ts` (the snapshot route bodies), `bench/panels/world.js` (a Pending section), `src/player/target.ts`, `src/player/rule.ts`, `src/player/run.ts`, `src/player/score.ts`; tests beside the existing ones. No new dependency.

2. Pending states (`src/engine/pending.ts`, `src/engine/engine.ts`, `src/server/routes.ts`, `bench/panels/world.js`). Multi-step actions share one shape: an action opens a pending state that the clock will close at a tick unless someone resolves it first. The clock's schedule is already the one home of every such deadline (clock.ts:29-58: a depart's arrive, an offer's lapse), so a pending state is a schedule entry, and nothing about it is stated a second time: `pendingOf(rows, defs, tickMinutes, events)` derives each one by running the engine's own rules and reducers. For each schedule entry it returns `{ opened: <the cause event: id, subkind, actor, targets, payload>, due: { at, fires: <the entry's subkind>, after }, resolutions: [{ by, action, after }] }`, where `opened` is the event in `events` whose id is the entry's cause (the log is the one record of what opened it: a schedule entry carries only its cause's id, clock.ts:35, and the store reads events only by seq range, store.ts:84), and `resolutions` are the actions, among every verb from `verbs()` by every person with each field over `fieldIds(field, snapshot)` (a placeholder line where it returns null, free text), that `rule()` records now and after whose events, applied to a copy of the rows through `applyPart` (the composition replay.ts:18 uses), that entry is gone from the schedule; and each `after` is `{ holders, locations }`, the item holders and person locations of the rows reached. The draft-to-event step `record()` performs (engine.ts:127) is exported once and used by both, never copied. `fieldIds(field, snapshot)` in `rules.ts`, beside `verbs()` (rules.ts:50), the one home of each verb's fields, owns the ids a field ranges over: `exit` every room's exits, `target` every person, `item` every item, and null for `words`, free text; the driver's `fill()` (actions.ts:41) draws its whole-world choice from it, keeping its own bias towards the actor and its absent, empty and inherited-key draws, so the mapping has one home. `engine.pending()` is its own accessor, passing the live rows, the definitions, the tick length and its own `events()` (engine.ts:76), never part of `snapshot()`, which the engine calls on its own apply path four times per act or step (engine.ts:101, 110, 112, 149), so the engine's recording and the driver's oracles never pay for the sweep; the `/api/snapshot` route (routes.ts:102) composes it into its body as `pending` beside the snapshot's fields, and every route body that hands the page a snapshot does the same (the reset's, routes.ts:159); `buildSnapshot()` and `snapshot()` are unchanged. On the committed world an offer gives two resolutions, the target's accept (after: the target holds the item) and refuse (after: the giver does), and its due firing is the lapse (after: the giver does); a transit gives no resolution and its due firing is the arrival (after: the walker in the destination room). Nothing in `pending.ts` names a verb, a subkind or a part: a later trade or unlock that schedules its deadline is a pending state with its resolutions the day its rule exists. The page renders a `Pending` section from `pending`, one line per state built by code from its fields ("exchange.offer e1 by rogue to glitch, data-shard: resolved by glitch accept, glitch refuse; at tick 2 the clock fires exchange.lapse"; "physical.depart e3 by glitch: no one resolves it; at tick 1 the clock fires physical.arrive"), so Jev's state and a person watching read the same thing; it adds no control.

3. The target (`src/player/target.ts`, `src/player/goal.ts`). The run's target is a typed plan: the end state the run is for and the ordered typed actions the model expects to reach it, never one action alone. `src/player/goal.ts` owns the end-state vocabulary the player and score share: `expectSchema` (`{ holder: { item, person } }`, `{ location: { person, room } }`, `{ said: { person, subkind } }`, `{ outcome: \"no-such-action\" }`, moved here from score.ts:30 unchanged) and `holds(expect, base)` (moved from score.ts:91 unchanged, reading `/api/snapshot` and `/api/events` through the bench's routes). `target(instruction, page)` gives the model the instruction, the verbs the page offers with each verb's fields, the people, items, exits and rooms the page shows, and the speech kinds, and asks for `{ kind: \"goal\", expect, needsWords, steps }` or `{ kind: \"no-such-action\", reason }`, where `steps` is an ordered list of typed actions `{ actor, verb, fields: { target?, item?, exit? } }`, actions by anyone the end state needs (an offer and its accept, a walk and then a word), with the clock's steps left out because code steps it; `steps` defaults to empty, so a target with none still parses and the run is led by Jev from its first loop. The speech kinds are the registry's subkinds whose kind is speech (events.ts:75 `subkinds`, filtered by `kindOf` === \"speech\", events.ts:116), since the page shows a subkind only once such an event is in its history and adding a subkind is one registry entry with no page change (world-bench design.md:47); the registry read types the goal and drives nothing. Code checks every id the target names: a person, item or room the end state names that the page does not show, a subkind that is not one of those speech kinds, or a step's verb, actor, target, item or exit the page does not offer, is `no-such-action` with the mismatch named, whatever the model said; the player still acts only on what the page shows. The schema keeps the recorded `action` kind (target.ts:14 before this change) as a type only, so run files written before this change still parse; the player never produces it. Whether the run writes words is decided by code, never by the model: it does when the end state is of kind `said` or any step's verb has a `words` field in `verbs()` (rules.ts:50); the model's `needsWords` stays in the schema so recorded targets still parse, and decides nothing. When the run writes words, `words(goal, page)` asks the model for the line (the only free text in the run), which every step whose verb takes words types; Jev never writes it.

4. The rule (`src/player/rule.ts`). Pre-registered in code with `RULE_AUTHOR`; `T_DONE` and `T_ACT` keep their calibrated values (rule.ts:16-17 before this change). Each loop asks Jev, over a state rendered by code (the instruction, the end state in words built by code from `expect`, the plan's steps in words with each marked done or not, the words if any, then the page text, which carries the pending states), one noul `done` and one noul per candidate, all in one `decide` call; the answers are recorded every loop. Then code decides, in this order: (a) `reached` when `holds(goal.expect)` is true on the bench now, the done noul recorded and deciding nothing, the outcome keeping it as `done`; (b) `resolve` when a pending state stands between now and the goal: the first entry of the snapshot route's `pending` with a resolution whose `after` satisfies the end state (the same predicate `holds` applies to a snapshot, `satisfies(expect, after)`, one function for both) gives the next action, that resolution's next form move, recorded with the pending state it serves; when no resolution does but the entry's `due.after` satisfies it (an arrival), the next action is `press Step`; (c) `wait` when a pending state the plan's last performed step opened stands with no resolution (a walk in transit): the next action is `press Step`, recorded with the pending state it waits on, since the plan's next step cannot be performed by a person in transit and the clock alone closes the entry; (d) `plan` when the plan has a next unperformed step: that step's next form move, recorded with the step's index; a step is performed once a press Act the plan led to records an event whose actor is the step's actor (read through `/api/events`, the route the run already reads), and a press Act that records nothing is a refused step, which ends the plan for the rest of the run; (e) otherwise `choose()` performs the highest candidate at or above `T_ACT`, or stops `stuck`, with `press Step` removed from the candidates while any pending state has a resolution whose `after` satisfies the end state. The next form move of a resolution's or a step's action is derived from the controls as read by the one function `nextMove(action, controls)` (rule.ts:101): the first control among actor, verb and each of the action's fields whose value differs from the action's gives the candidate `set <label> to <value>`, then `type the words into words` when the verb takes words and the field does not hold them; when all agree, `press Act`. When the derived move is not among the page's candidates, the loop stops `stuck` naming the pending state or the step, never guessing. Nothing in (b), (c) or (d) names an action kind: an offer, an arrival, a word and any later pending state are served by the same lookup.

5. The loop (`src/player/run.ts`). `runPlayer` (run.ts:278 before this change) keeps its shape: each loop it reads the page, reads the snapshot route's body (its pending states), the history's events since the plan's last press Act, and whether the end state holds through the bench's routes, renders the state, asks the rule, prints the loop (the state text sent, every question with its answer, the decision with the pending state or step it serves, and the action performed or the stop) as it happens and appends it to `loops.jsonl` with `held`, performs the action in the browser and waits for the page to settle. It ends on `reached`, `stuck`, `no-such-action`, the loop ceiling, or a refusal from either client, which it names. `run.json`'s target is the typed plan.

6. Goals and scoring (`src/player/score.ts`, `corpus/goals/`). A goal file's `expect` is the end state of `src/player/goal.ts`, checked by code (`holds`) against the run's final `/api/snapshot` and `/api/events`. `score` keeps its refusal of a goal file whose `author` equals `RULE_AUTHOR`. With `--sweep` it replays the recorded loops over a grid of `T_ACT` values with reached taken from each loop's recorded `held` and `resolve`, `wait` and `plan` loops followed as recorded, since code chose them, `T_DONE` held at its calibrated value in every row of the `{ done, act, held }` results, and prints the best; the calibrated constants are not re-swept. The blind set for the C9 walk is written after the merge, by a fresh agent that has read neither `rule.ts` nor any earlier blind set (blind-1 and blind-2 are spent: their misses shaped this change) and is not the rule's author, which is why its score is a post-merge walk: a blind set that exists while the rule is written is not blind.

7. Proof. Pending states: `pending` on a booted world after an offer and after a depart equals values derived by hand (opened, due with its after, the resolutions with theirs), through `engine.pending()` and through `/api/snapshot`, with `engine.snapshot()` carrying none, and stepping to an offer's `due.at` records its lapse and empties `pending`; the page shows each with its resolver, verbs and expiry. Player, against local stand-ins for the decisions endpoint and the chat completions endpoint returning scripted answers, with the real browser on a hosted bench: with scripted nouls that score `press Step` above every other candidate on every loop after the offer, each give goal (a holder end state reached by offer then accept) reaches its end state with no `exchange.lapse` in the run's history and no Step pressed while the offer stood, and a run with the derivation removed lapses (the mutation); a run whose done noul is 0.0 on every loop ends reached on the loop its end state holds, and one whose done noul is 0.99 does not end reached before it holds; an end state naming an item the page lacks, or a speech kind the registry lacks, ends in `no-such-action` without a loop, while a said goal on a fresh bench is checked against the registry's speech kinds and runs; the driver's seeded run still passes every check with `fill()` drawing from `fieldIds()`; score checks each typed expectation and its sweep follows resolve loops with T_DONE fixed; the constants equal the calibration score's recorded pair. Plan: with a stand-in target whose steps are the giver's offer then the receiver's accept, and scripted nouls that score every candidate below `T_ACT`, each give goal reaches its end state through `plan` and `resolve` loops alone; with steps of a walk then a say-to (Mux west to the bar, then a say-to Glitch), the run presses Step through `wait` loops until Mux arrives and then performs the say-to; a step naming an exit the page lacks ends in `no-such-action`; a step the bench refuses ends the plan and the next loop is led by `choose()`; a target with no steps runs as Jev leads.

Acts on the gap: It supplies what the gap names: the engine derives each pending state from the clock's schedule, with its resolutions and their results found by running its own rules and reducers, served by its own accessor and shown on the page; the player's target becomes a typed plan, an end state checked by code, which decides reached, and the ordered actions code performs step by step; and code resolves or waits out a pending state that stands between now and the goal or between two steps, before the clock's expiry, with no action kind named.

## Commitments

- A pending state is a clock schedule entry, and its resolutions and their results are derived by running the engine's own rules and reducers on a copy of the rows, served by its own engine accessor through the bench's routes, never on the engine's apply path, and shown on the page; nothing about a pending state is stated a second time and no verb, subkind or part is named in deriving it.
- The player's goal is a typed end state from the closed set (holder, location, said, no-such-action), checked by code against the bench; reached is that check, never a model's claim, and the done noul is recorded but decides nothing.
- While a pending state whose resolution leaves the goal's end state stands, the next action is derived by code from that resolution and the clock is never stepped past its expiry; no action kind is named in that derivation.
- An end state naming a person, item or room the page does not show, or a speech kind the registry lacks, ends in no-such-action naming it; nothing invents a person, item, room or speech kind.
- The ids a verb's field ranges over have one home, fieldIds() beside verbs(), read by the pending sweep and the driver alike.
- Every loop's request, answers and decision are printed as they happen and recorded, the done noul included.
- T_DONE and T_ACT keep their calibrated values; nothing is re-tuned against a blind set, and the blind walk uses a fresh set written by an agent that has read neither the rule nor an earlier blind set.

## Sacrifices

- The blind goal set and its score come after the merge, as a walk: a blind set that exists while the rule is written is not blind, so the worktree proves scoring on the calibration set and the blind score runs once the rule is on main. (not a case: no blind set can exist before the rule is on main: the rule's author is the builder, and the set is written against the merged rule by another agent)
- Jev and the model are not deterministic, so a player run is not reproducible from its parameters; the corpus is committed because the run cannot be re-made. (0 of 32 32 moments, 3 reps each, 96 answers)
- The calibrated T_ACT was set under the rule before this change (no pending precedence, reached by the done noul) and is kept, not re-swept, by the operator's condition; the calibration score records the old rule's runs. (9 of 9 corpus/goals/calibration.score.json)
- Every snapshot the bench serves tries each verb by each person over the world's ids through the rules to find the pending states' resolutions; the cost grows with people, verbs and ids, bounded on the committed world and paid only while a schedule entry stands. (not a case: a cost on every snapshot route read while a schedule entry stands, not a usage case: the committed world has three people, three items and two exits, so the tries are bounded by people times verbs times ids, and the engine's own apply path never pays it)
- A pending state is seen only when it has a schedule entry; a later wait with no deadline would need one before the player could see it. (0 of 2 src/engine/clock.ts schedulePart)
- The said end state's speech kinds are read from the engine's registry, not from the page: the goal typing knows a subkind the page does not yet show. (not a case: the registry read only types the goal and drives nothing: every action the player performs is still a control the page shows)

## Risk

If the model's plan is wrong (a step by the wrong person, or a step the rules refuse), the first refused step ends the plan and Jev's per-control nouls lead from there, which blind-2 showed fail on a give's opening move; the plan's steps are checked against the page so a wrong name ends in no-such-action rather than a loop to the ceiling. If the derived move is missing from the page, the loop stops stuck naming the pending state or step rather than letting Jev press Step. If pending were derived inside snapshot(), every act and step would pay the verb-by-person sweep four times; the separate accessor keeps the apply path and the driver's oracles unchanged. If the blind set is written by an agent that has read the rule or an earlier blind set, its score means nothing, which is why blind-3 is written by a fresh agent after the merge.

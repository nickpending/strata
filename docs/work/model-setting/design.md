# Design: model-setting

## Purpose

The player's language model, which writes the target and the words, becomes a named setting. A run and a score take it as a flag and record it in every run and score file. A score made under a named model lands in a file of its own beside the committed scores. A compare command then sets two models' scores of the same goal sets side by side as a loss report: what the candidate loses and gains against the baseline, per set and per goal, with the reason for each loss readable. It makes no verdict. With it, GLM-5.3-flash and Haiku 5.5 are both scored on today's code over the four goal sets and the report is committed. rudy reads it and decides the switch, and the default stays Haiku until he does.

## Form

One flag over the one model id, one score path per named model, two fields per goal and a compare command, then one measured comparison.

1. The setting (`harness/src/words.ts`, `harness/src/run.ts`). `WORDS_MODEL` (words.ts:11) is renamed `DEFAULT_MODEL`, its value unchanged, `anthropic/claude-haiku-5.5`. words.ts exports `type ModelOptions = ClientOptions & { model?: string | undefined }`, and `complete()` posts `model: options.model ?? DEFAULT_MODEL` (words.ts:39), so the target (target.ts askTarget) and the words (words.ts words) share the one setting, as they share the one constant today. `RUN_FLAGS` (run.ts:180) gains `model: { type: "string" }`, and `RUN_USAGE` gains `[--model <provider/model>]`. `optionsFromFlags()` (run.ts:201) refuses a `--model` that does not match `^[A-Za-z0-9][A-Za-z0-9._-]*/[A-Za-z0-9][A-Za-z0-9._:-]*$` with the usage message `--model must be an OpenRouter model id, <provider>/<model>, got "<value>"`, so a run and a score both exit 2 on it. It sets `model: { ...client(text("model-endpoint")), model: text("model") }`. `DriveOptions.model` becomes `ModelOptions`, and `DriveOptions` gains nothing else. `drive()` records `parameters.wordsModel: options.model.model ?? DEFAULT_MODEL` (run.ts:415), the field every run.json already carries, so its name and meaning are kept. Jev's `JEV_MODEL` (jev.ts:11) is untouched.

2. The score's model and its path (`harness/src/score.ts`). `ScoreFile` (score.ts:73) gains `model: string`, the model its runs were made with (the value run.json's `wordsModel` records), set beside `rule`. `score()` (score.ts:155) writes to the path an exported `scorePath(goalsPath, set, model)` gives, the one place the path is derived: `<set>.score.json` when `run.model.model` is undefined, exactly as today. When a model is named it writes to `<set>.<slug>.score.json`, where `slug` is the model id with every character outside `[A-Za-z0-9._-]` replaced by `_` (`z-ai/glm-5.3-flash` becomes `z-ai_glm-5.3-flash`). So a score made under a named model never writes, reads or replaces the committed `<set>.score.json`, which C9 (tests/rule.test.ts:17) reads. That holds even when the named model is the default's id. The set-name refusal (score.ts:245) is unchanged; its message names the path the score would be written to.

3. What each goal records (`GoalScore`, score.ts:54). Two fields are added, read from the run's record at the point score() builds the entry (score.ts:165-182). The first is `target: "valid" | "invalid" | "unanswered"`: `valid` when `record.target` is not null, i.e. the model's answer parsed as JSON and passed the target schema (a target checked() turned into no-such-action is still valid); `invalid` when the run stopped at call `target` with kind `parse`; `unanswered` for any other run, one stopped before or at the target call by a config, network, status, boot, page, browser or bench refusal. The second is `words: { kind: "written"; text: string } | { kind: "refused" } | { kind: "none" }`: `written` with `record.words` when the run wrote them; `refused` when the run stopped at call `words` with kind `parse`; `none` otherwise. ScoreFile gains `targets: { valid: number; asked: number }` (asked counts valid plus invalid) and `words: { written: number; refused: number }`, each summed over perGoal.

4. The compare command (`harness/src/compare.ts`, new; root package.json script `compare`: `bun run harness/src/compare.ts`). `bun run compare --baseline <model> --candidate <model> --goals <file> [--goals <file> ...]` finds, for each goal file, the two score files through the one exported path function score() writes through (`scorePath(goalsPath, set, model)` in score.ts, item 2), never a second derivation of the slug. It exits 1, naming the file and the field, when any of these hold: a file is missing; a file's `model` is not the model named; the two files' `rule.thresholds` differ from each other or from `REGISTERED` (rule.ts:29); their perGoal ids differ from the goal file's ids in order; or a run directory a lost or gained goal names has no run.json. It decides nothing and states no verdict: no held, holds or did-not-hold of a set or of the whole appears in its output. It writes `<dir>/<slug(candidate)>.vs.<slug(baseline)>.compare.json`, `dir` being the first goal file's directory, and the same content rendered as markdown in `.compare.md`, in this order. (a) Per set, both models side by side: `reached.held` of `reached.of`, `targets.valid` of `targets.asked`, `words.written` and `words.refused`, and `costUsd` with `unreportedCosts`, each read from that model's score file. (b) Losses first: every goal, over all sets in goal-file order, whose baseline entry has `held` true and whose candidate entry has `held` false. Each shows its set, id, instruction and expectation, and for each model: the outcome; the target as the run recorded it (run.json `target`, the typed end state and its steps, or the no-such-action reason); or, when the target was refused, the refusal's kind and message (run.json `stopped`). These come from the run.json each goal's `run` path names, the one record of what the model typed, so the reason a goal was lost can be read. (c) Gains: every goal whose candidate entry is held and whose baseline entry is not, in the same form. (d) Words: every goal's `words` from both models side by side (the line, refused, or none). Nothing scores them. Every number and line in both files is rendered by code from the score files and run.json files; nothing is typed, and compare decides nothing about the default.

5. The comparison, run once in the job's worktree after the code above passes the gate, with the real endpoints and the registered thresholds. These eight scores run in this order, recorded as commands in the job's evidence: `bun run score --goals corpus/goals/calibration.json --sweep --tick-minutes 10 --model anthropic/claude-haiku-5.5`; the same for blind-1, blind-2-spent and blind-2 without `--sweep` (calibration is the rule author's set and scores only with it, score.ts:253; its sweep is recorded and moves no threshold); then the same four with `--model z-ai/glm-5.3-flash`. That is 94 runs, about $0.07 (docs/work/model-setting/shape/cost-split.txt). Then `bun run compare --baseline anthropic/claude-haiku-5.5 --candidate z-ai/glm-5.3-flash --goals` with the four goal files. If any goal's `target` comes out `unanswered`, the comparison halts to the orchestrator, naming the run and its refusal. It is never counted, and never re-run until the orchestrator rules, because a provider failure is not the model's answer. The eight score files, their runs and the two compare files are committed together in one commit of the job. The committed `<set>.score.json` files are left byte-identical. `DEFAULT_MODEL` stays `anthropic/claude-haiku-5.5`. The lane's result reports the per-set numbers, the losses and the gains from the compare files. rudy decides the switch after he reads the report, and this work makes no switch.

Acts on the gap: The gap is that no setting names the player's model and nothing measures a candidate against Haiku. The flag on RUN_FLAGS is the setting, recorded in every run and score. A named model's score lands beside the committed ones, so two models' scores of one set can stand together. Each goal records whether its target was schema-valid and what words it wrote. compare turns two models' scores into the loss report rudy asked for, what GLM loses and gains and why. The job then fills the gap with the measurement itself: GLM and Haiku scored on the same code over all four sets, the report committed for rudy to decide on.

## Commitments

- The player's model is one setting, `--model`, on every run and score; with none named the target and words are asked of anthropic/claude-haiku-5.5, as today.
- A model id that is not <provider>/<model> is refused at the command line with exit 2, before any bench boots or any call is made.
- Every run.json's parameters.wordsModel and every new score file's model name the model the runs were made with.
- A score made under a named model writes only <set>.<slug>.score.json and never writes, reads or replaces <set>.score.json, so C9's calibration record and every committed score stay byte-identical.
- Each goal's score entry says whether its target answer was schema-valid, schema-invalid or never answered, and whether its words were written (with the line) or refused; each score file sums them.
- compare writes a loss report and no verdict. Per set, it puts both models' reached count, schema-valid targets of asked, words written and refused, and cost side by side. Then, in order, it lists every goal the baseline held and the candidate did not (with both models' outcome and recorded target or refusal), every goal the reverse, and every goal's words from both models, all rendered by code from the score and run files.
- compare refuses two score files that name another model, were made at other thresholds than the registered ones, or score other goals, so the report only ever sets like-for-like runs side by side.
- GLM-5.3-flash and Haiku 5.5 are each scored once per set on the same built code over calibration, blind-1, blind-2-spent and blind-2, and the scores, their runs and the comparison are committed together.
- A comparison run that a provider failed (target unanswered) halts the job for a ruling; it is never counted for or against a model, and never silently re-run.
- The default model is not changed; Jev's model stays a constant; the harness still reads the world only over the bench's routes.

## Sacrifices

- Each model is scored once per set, so a goal listed as lost or gained can be run-to-run noise rather than the model (calibration went from 8 of 9 to 9 of 9 between two committed Haiku scores); the report shows the recorded target and outcome of each so rudy can read which, and a re-run is his call. (0 of 9 goals of corpus/goals/calibration.baseline.score.json and calibration.moved.score.json, two Haiku scores of calibration on the same rule (harness-package))
- Naming the default model on the command line writes a separate <set>.<slug>.score.json rather than the registered <set>.score.json, so the same model can have two score files for one set. (not a case: No reader confuses the two: C9 and the committed record read <set>.score.json by name, and compare reads only the named-model files and checks each one's model field.)
- Score files written before this carry no model, targets or words field, and the committed runs are not rewritten; compare reads only files written by this code. (6 of 6 corpus/goals/*.score.json)
- complete() sends the same request to both models, json_object with no max_tokens and no structured-output schema, so GLM is measured on today's request rather than one tuned for it. (not a case: This is the like-for-like comparison issue #3 asks for, not a usage path. GLM answered that exact request shape with parseable JSON (docs/work/model-setting/shape/glm-probe.txt).)

## Risk

If the score path were keyed on the model's value rather than on its being named, the Haiku re-score would replace calibration.score.json, and C9 would fail on today's flat sweep (issue #6). So a named model always gets its own file. If schema-valid were read from the outcome, a target checked() refused as no-such-action would count as invalid and blame the model for the page's vocabulary. So validity is read from whether record.target was set. If a provider failure counted as a schema-invalid target, a 402 or a timeout would score against whichever model it happened to. So an unanswered target halts and is never counted. If compare reported only counts, a model losing two goals on one set and gaining two on another would read as level, and rudy could not see what is lost. So every lost goal is listed by id with both models' recorded targets, and a mutation that drops a lost goal from the losses section must turn compare's test red. If compare took a goal's reason from anything but the run.json its score entry names, the reason shown could be another run's. So it reads that file and refuses when it is missing. If compare accepted score files without checking their model and thresholds, a stale or mislabelled file would stand in the report. So it refuses them. If the slug kept a /, the score path would name a directory. So every character outside [A-Za-z0-9._-] becomes _, and the id's pattern forbids a leading dot.

# Design: structured-output

## Purpose

The player's model is asked for the target and the words by OpenRouter json_schema structured outputs built from the zod schemas that check them, on endpoints that enforce them, with zod kept as the backstop. An answer that still fails to parse is asked once more with the identical request, which carries no hint. Every attempt is a recorded call with its cost and, when refused, the model's whole answer. Score and compare count each model's retries and show what they rescued. Scores and reports made under this request land on paths that name it, so GLM and Haiku are re-scored on all four sets and a new loss report is written beside the old one, which stays as it is.

## Form

One request, one retry and one record of every attempt in complete(), carried through the run record, the score and the compare, then one measured comparison.

1. The request (`harness/src/words.ts`, `complete()` at words.ts:34). words.ts exports `REQUEST = "json-schema-retry"`, the name of the request complete() sends. `complete(prompt, schema, name, options)` gains `name` ("target" from askTarget, target.ts; "words" from words()) and posts `model`, `messages` as today, `response_format: { type: "json_schema", json_schema: { name, strict: true, schema: wireSchema(schema) } }` in place of json_object (words.ts:45), `provider: { require_parameters: true }` (so an endpoint without structured_outputs never serves it: docs/work/structured-output/shape/openrouter-require-parameters.md:13) and `usage: { include: true }`. `wireSchema(schema)`, exported, is `z.toJSONSchema(schema, { io: "output" })` with every `oneOf` key renamed `anyOf`, because every Haiku endpoint refuses oneOf (probe-oneof.txt:2) and target's branches are disjoint on kind's const, so anyOf admits exactly the same answers. The prompts are unchanged. The zod parse after it is unchanged: providers do not enforce minLength (probe.txt:18), so a provider-shaped answer can still be refused.

2. The retry and the attempts (`complete()`). An attempt is one post that came back with a body. When an attempt's answer is refused with kind `parse` (the body has no message content, the content is not JSON, or it fails the zod schema), complete() posts the identical body object once more; no prior answer, error or hint is added, so the second request is byte-identical to the first. Neither call sets temperature or seed (words.ts, target.ts), so the retry is a fresh sample at the provider's default, not a guaranteed repeat of the first answer: a rescue is a second draw. A config, network or status refusal is never retried, a second parse refusal is final, and a parsed target that checked() turns into no-such-action (target.ts:162) is not a refusal and is never retried. `Completed<T>` becomes `({ ok: true; value: T } | { ok: false; refusal: Refusal }) & { attempts: Attempt[] }`, with `Attempt = { costUsd: number | null; retry: boolean; refused: { message: string; answer: string | null } | null }`: `answer` is the message content exactly as sent, whole (null when the body had none), and `message` the refusal's message, which keeps its 80-character excerpt (words.ts:58). The ok result's `costUsd` is replaced by `attempts`. askTarget() and words() pass `attempts` through unchanged.

3. The run record (`harness/src/run.ts`). `Call` (run.ts:125) gains optional `retry?: true` and `refused?: { message: string; answer: string | null }`, set from the attempt and left out when false or null, so a run.json written before reads as one. In play(), right after the target call (run.ts:579) and the words call (run.ts:608), every attempt is recorded through hooks.call() with purpose `target` or `words`, its cost and those two fields, before the ok check, so a refused attempt and a retry are each a call with its own reported cost in `calls`, `costUsd` and `unreportedCosts`. The stop on a refusal is unchanged: `{ ...refusal, call: "target" | "words" }`. `parameters` gains `request: REQUEST` (run.ts:423), typed optional so earlier run.json files still read.

4. The score (`harness/src/score.ts`). `GoalScore` (score.ts:57) gains `retries: { asked: number; rescued: number }`, read from the run's calls: `asked` the model calls with retry true, `rescued` those of them with no `refused`. `ScoreFile` (score.ts:86) gains `request: REQUEST` and `retries: { asked; rescued }` summed over perGoal. `scorePath()` (score.ts:193), still the one derivation, gives `<set>.<slug>.<REQUEST>.score.json` for a named model, so `<set>.z-ai_glm-5.3-flash.json-schema-retry.score.json` beside the committed `<set>.z-ai_glm-5.3-flash.score.json`, which it never writes, reads or replaces; the unnamed `<set>.score.json` is unchanged. A target's validity and words keep their meaning: `valid` and `written` describe the final answer.

5. The compare (`harness/src/compare.ts`). readScore() (compare.ts:94) also refuses a score file whose `request` is not REQUEST, naming the file and the field, so a file made under another request never stands in the report. `Comparison` gains `request`; the report is written to `<candidate>.vs.<baseline>.<REQUEST>.compare.json` and `.md` (compare.ts:215), never over the committed `<candidate>.vs.<baseline>.compare.*`. `Side` gains `retries`, and the per-set table (compare.ts:279) gains the columns `retries asked` and `retries rescued`. `GoalRun` gains `refused: { purpose: string; retry: boolean; message: string; answer: string | null }[]`, every refused call of that run.json in order, and each lost or gained goal's line shows each refused answer whole. A section `## Retries`, after Gains and before Words, lists every goal over all sets in goal-file order whose score entry for either model has `retries.asked` above 0, each with its set, id and instruction, and for each model whether it was held, its retries asked and rescued, and each refused answer with its message, in call order, so a rescued answer and the first answer it replaced read side by side. Every line is rendered by code from the score files and the run.json files their entries name; the report states no verdict.

6. The comparison, run once in the job's worktree after the code above passes the gate, with the real endpoints and the registered thresholds, as model-setting item 5 ran it: `bun run score --goals corpus/goals/calibration.json --sweep --tick-minutes 10 --model anthropic/claude-haiku-5.5`, the same for blind-1, blind-2-spent and blind-2 without `--sweep`, then the four with `--model z-ai/glm-5.3-flash`, 94 runs, then `bun run compare --baseline anthropic/claude-haiku-5.5 --candidate z-ai/glm-5.3-flash --goals` with the four goal files. A goal whose target comes out `unanswered` halts the comparison to the orchestrator, naming the run and its refusal, and is never counted or re-run until the orchestrator rules. The eight new score files, their runs and the two new compare files are committed together; the eight committed named-model score files, the committed compare files and every `<set>.score.json` stay byte-identical; DEFAULT_MODEL stays anthropic/claude-haiku-5.5. The lane's result reports the per-set numbers, the retries, the losses and the gains from the new compare files.

7. Tests (strata-side under tests/, over the stand-ins of tests/stand-ins.ts, which keep every request body). The reproduction: a run whose model stand-in answers the words call first with GLM's recorded garbled answer (corpus/runs/2026-11-01T21-15-09-855Z) and then with a valid line ends reached, with calls target, words (refused, its answer whole, longer than 80 characters), words (retry, not refused), each with its cost; on the code before this change the same run stops at parse at words with no words call recorded. A target answered not the shape and then valid reaches the same way; one answered unparseable twice stops at parse at target after exactly two requests with both calls recorded; a status 500 and a no-such-action from checked() are each asked once. The retry's request body deep-equals the first. A test pins the request body complete() sends (response_format json_schema with its name and strict, provider.require_parameters, and no other request field) together with REQUEST's value, so a change to the request that does not rename REQUEST turns it red. The target and words request bodies carry json_schema with name target and words, strict true, require_parameters true and no oneOf anywhere in the schema. The parse test with no choices (player.test.ts:648) now sends two requests and records two refused calls with answer null. Score: each entry's retries and the file's sums, the path naming REQUEST, and a file at the pre-change path left byte-identical. Compare: refuses a file of another request; the retries columns; the Retries section lists a retried goal with its refused answer, and removing that section or a goal from it turns a test red.

Acts on the cause: The cause is that complete() asks for any JSON instead of the schema it checks against, ends the run on the first answer that fails that check, and returns that answer with neither its text nor its cost. The request now carries that schema to endpoints that enforce it, a refused answer is asked once more with the identical request before the run ends on it, and every attempt is returned and recorded as a call with its cost and its whole answer, so no part of the condition remains: the shape is asked for, one format glitch no longer ends the run, and no answer or cost goes unrecorded.

## Commitments

- The target call and the words call each send OpenRouter json_schema, strict, built from the very zod schema the answer is then checked against, with require_parameters true, so only endpoints that enforce a requested shape serve them; the zod check stays after it.
- An answer refused at parse (no content, not JSON, or not the zod shape) is asked exactly once more by a request byte-identical to the first, a fresh sample at the provider's default since no temperature or seed is set; no other refusal, and no target checked() refuses, is ever asked again.
- Every model attempt that came back with a body is a call in run.json with its own reported cost, marked when it was the retry, and carrying the model's whole answer and the refusal's message when it was refused.
- Each score entry and score file count the retries asked and rescued, and the compare report shows them per set for both models and lists every goal where a retry was asked, with each refused answer.
- Scores and reports made under this request are written to paths that name it, never over the files made before it, and compare refuses a score file made under another request.
- GLM-5.3-flash and Haiku 5.5 are each re-scored once per set on calibration, blind-1, blind-2-spent and blind-2 under the new request, and the scores, runs and report are committed together; a provider-failed target halts for a ruling.
- DEFAULT_MODEL stays anthropic/claude-haiku-5.5; the prompts are unchanged; the harness still imports nothing from the engine or the server.

## Sacrifices

- Providers do not enforce minLength or trim, so a provider-shaped answer can still be refused by zod; the zod check and the one retry cover it rather than the schema. (4 of 4 the empty-line probes of docs/work/structured-output/shape/probe.txt, both models, both schema variants)
- require_parameters keeps the request off every endpoint that lacks structured_outputs, so fewer providers can serve either model, and a model with none would be refused with a status the comparison halts on. (10 of 50 the OpenRouter endpoints of z-ai/glm-5.3-flash and anthropic/claude-haiku-5.5 (docs/work/structured-output/shape/endpoints.txt))
- The committed GLM-vs-Haiku scores and report cannot be read or regenerated by the new compare, which reads only files of this request; they stay committed as the json_object record. (10 of 10 the committed named-model score files and compare files in corpus/goals)
- A goal the retry rescued counts as held for its model, so the reached count measures the model with one hint-free resample; the retries columns and section show each one so rudy can discount it. (3 of 177 corpus/runs/*/run.json, runs stopped on a parse refusal at target or words, the runs a retry would have reached)
- Neither call sets temperature or seed, so the byte-identical retry is a fresh sample at the provider's default, not a guaranteed repeat of the first answer: a rescue measures a second draw. (3 of 177 corpus/runs/*/run.json, runs stopped on a parse refusal at target or words, each of which a retry would resample)
- A refused answer is kept whole in run.json, however long the model's garbled output runs. (3 of 177 corpus/runs/*/run.json, runs with a refused model answer)

## Risk

If the schema were sent as zod gives it, every Haiku call would be refused with 400 for oneOf and the comparison would halt on Haiku alone; the rename to anyOf is what lets both run. If the request left require_parameters off, a request routed to an endpoint without structured_outputs would have the schema silently ignored, and GLM would again be measured on any-JSON for some goals; requiring it makes such a run a status refusal the comparison halts on instead. If the retry carried the first answer or its error, it would hand the model code's hint, the re-ask already-held ruled out; it re-sends the identical body, and a test compares the two request bodies. If a status or no-such-action were retried, a provider failure or the page's vocabulary would get a second try a format glitch does not need; only a parse refusal is retried. If only the final attempt were recorded, a refused first attempt's cost would be lost as it is today and the retries could not be counted; every attempt is a call. If the score path kept <set>.<slug>.score.json, the re-run would overwrite the scores the old report names and the old report would describe runs it no longer matches; the path names the request. If compare read a score file of another request, a json_object score could stand beside a json_schema score as like for like; it refuses it.
